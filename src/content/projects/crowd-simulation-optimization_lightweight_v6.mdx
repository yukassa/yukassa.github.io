## 概要

仮想的な通行人がスタート地点からゴール地点へ移動する様子をブラウザ上で観察し、**移動ルールや空間条件の違いによって集団の流れがどう変化するかを比較・評価できる人流シミュレータ**です。

シミュレーションでは、 **「目的地までどの道筋で進むか」を決める処理（大域経路探索）** と、 **「近くの人との衝突をどう避けるか」を決める処理（局所回避）** を分離しています。それぞれ2方式を用意し、**同じマップ、エージェント数、移動パラメータ、乱数条件、評価時間**を使って4通りの組み合わせを比較できます。

ブラウザ上では人流をリアルタイムに観察しながら、エージェント数や歩行速度などの条件を変更したり、壁オブジェクトの配置、異なる方向へ進む人流を追加することができます。また、画面描画を省略した評価用シミュレーションで **平均到達時間・最大混雑度・到達率** を計測し、移動モデルや壁配置による違いを数値で比較します。

さらに、配置済みの壁オブジェクトについて、 **「どこへ配置すると、より短時間で到達しやすく、混雑や未到達を抑えられるか」** をGA（遺伝的アルゴリズム）で探索します。人流を可視化するだけでなく、**条件変更 → 観察 → 定量評価 → 配置探索**までを一つの検証フローとして扱える構成にしています。

## 背景・目的

創発現象やマルチエージェントシステムに関心があり、**個々のエージェントに単純なルールを与えたとき、その相互作用から集団全体としてどのような振る舞いが生まれるのかを観察したい**と考えたことが、このプロジェクトの出発点です。

まずは日常でもイメージしやすく、複数の人が互いに影響しながら移動する **人流** を題材にしました。

単に人が動く様子を可視化するだけではなく、**移動モデルや壁配置を変更し、平均到達時間・最大混雑度・到達率という共通の指標で比較できること**を重視しています。

さらに、そこで得た評価結果を使って、**配置済みの壁をどこへ移動させると人流が改善するかを探索する**処理へつなげました。GAによる探索では、候補ごとに描画を行う必要がないため、同じ移動ロジックを使った描画なしの評価用シミュレーションを繰り返し実行しています。

## 技術的な課題と工夫

### 1. 「経路を選ぶ処理」と「人を避ける処理」の分離

人の移動を考えると、

1. **目的地まで、どの道筋で進むか（大域経路探索）**
2. **近くに他の人がいたとき、どう避けるか（局所回避）**

は別の問題です。

そこで、この2つを別々の処理として実装し、組み合わせを切り替えられるようにしました。

#### 目的地までの経路を選ぶ方法（大域経路探索）

| 手法           | 概要                                                                                                                       |
| :------------- | :------------------------------------------------------------------------------------------------------------------------- |
| **A\***        | 現在位置からゴールまで、壁を避ける経路を探索し、その経路に沿って移動する                                                   |
| **Flow Field** | 各地点からゴールへ進む方向をあらかじめ計算・マッピングしておく方式。多数のエージェントがマッピングされた方向に沿って進む。 |

#### 近くの人を避ける方法（局所回避）

| 手法                       | 概要                                                                 |
| :------------------------- | :------------------------------------------------------------------- |
| **Force-based separation** | 近くのエージェントから離れる向きに反発を加え、近距離では反発を強める |
| **Social Force Model**     | 周囲の人との距離に応じた指数的な反発を加える簡略モデル               |

大域経路探索と局所回避を別々の設定として持つことで、**2種の大域経路探索 × 2種の局所回避**の4通りを自由に組み合わせられる構成としています。

壁オブジェクトの追加・削除・移動時には通行可能領域を更新し、経路探索アルゴリズムを再計算することで、変更後の空間へ追従させます。

局所回避では、同じ方向へ進む人だけでなく、**異なる人流に属する通行人も互いに回避対象**としています。対向する人流や交差する人流でも周囲の人に反応するため、異なる人流同士の相互作用を観察できます。

### 2. リアルタイム観察と繰り返し評価の分離

ブラウザ上で人の動きを観察する処理と、多数の条件を繰り返し評価する処理では、必要な処理が異なります。

- **リアルタイムシミュレーション**  
  Go側で約50 ms間隔（20 Hz）でシミュレーションを更新し、計算済みのエージェント状態をWebSocketでブラウザへ配信します。
- **描画を省略した評価用シミュレーション**  
  条件を評価するときは、ライブ表示と同じ移動ロジックを再利用しながら、WebSocket配信や画面描画を行わず、固定時間だけシミュレーションを進めます。
- **HTTP APIによる評価・探索**  
  現在配置の評価、4通りのアルゴリズム比較、GAによる配置探索などの単発処理はHTTP APIとして分離します。

これにより、観察用と評価用で移動ロジックを二重実装せず、同じモデルをリアルタイム表示と繰り返し実験の両方に利用できる構成としています。

### 3. 比較可能な評価指標と再現性（⭐️パターン1）

移動モデルや壁配置を変えたときに「どちらの結果が良いか」を比較するには、見た目の印象だけではなく、同じ観点で結果を数値化する必要があります。また、シミュレーションやGA（遺伝的アルゴリズム）には乱数を使う処理が含まれるため、乱数条件まで固定して再実行できなければ、モデルや配置の違いによる差なのか、偶然生じた差なのかを判断しにくくなります。

そこで本システムでは、**人流の結果を共通の評価指標で数値化すること**と、**乱数条件を固定して同じ実験条件を再現できること**の2点を重視しています。

#### 評価指標

以下の3指標は、移動モデルや壁配置による結果の違いを、**「到達までの速さ」「混雑の大きさ」「ゴールまで到達できた割合」**という3つの観点から比較するための共通の評価軸です。GAによる壁配置探索でも、候補となる壁配置ごとに描画なしで人流シミュレーションを実行し、これらの指標を使って結果を評価します。

| 指標             | 内容                                                                 | 評価したいこと                       |
| :--------------- | :------------------------------------------------------------------- | :----------------------------------- |
| **平均到達時間** | ゴール到達までの時間。評価時間内に未到達の場合は評価時間上限を用いる | より短時間で目的地へ到達できるか     |
| **最大混雑度**   | 評価中に1つのグリッドセルで観測された最大エージェント数              | 一部の場所に人が集中しすぎていないか |
| **到達率**       | 評価開始時のエージェントのうちゴールへ到達した割合                   | 行き詰まりや未到達が発生していないか |

最大混雑度は実世界の「人 / ㎡」を推定するものではなく、条件間を比較するための簡易指標として扱います。

また、未到達のエージェントを平均到達時間から除外すると、到達率が低い配置ほど平均時間が短く見える可能性があります。そのため、未到達者には評価時間上限を到達時間として与え、全エージェントを平均へ含めます。

#### 乱数条件の分離

比較と最適化を再現できるよう、乱数を以下の2系統に分けています。

- `simulation_seed`: エージェントの初期位置など、評価シミュレーション側の乱数条件を固定するseed
- `optimizer_seed`: GAの初期個体・選択・交叉・突然変異など、探索側の乱数条件を固定するseed

**2つのseedをそれぞれ固定することで、同じ入力条件に対して評価シミュレーションとGA探索の両方を同じ乱数系列で再実行できる**構成としています。GAは近似的に解を探索するアルゴリズムですが、探索に使う乱数系列を固定すれば、同じ初期条件から同じ探索過程を再現できます。

なお、再現できるのは「同じ条件から同じ探索結果を得られる」という意味であり、その結果が数学的な最適解であることを保証するものではありません。

### 3. 比較可能な評価指標と再現性（⭐️パターン2）

シミュレーションを見て「こちらの方が流れが良さそう」と判断するだけでは、条件ごとの差を比較しにくくなります。

そこで、以下の3指標を共通の評価軸として使っています。

| 指標             | 何を見るか                                   |
| :--------------- | :------------------------------------------- |
| **平均到達時間** | 全体として目的地へどのくらい早く到達できたか |
| **最大混雑度**   | 一部の場所に人が集中しすぎていないか         |
| **到達率**       | 評価時間内に目的地へ到達できた人の割合       |

平均到達時間では、評価時間内に到達できなかった通行人も除外せず、評価時間の上限値を到達時間として扱います。

これは、到達できなかった人を除外することで、かえって「多くの人が到達できない条件の方が平均時間だけは短い」という評価になることを避けるためです。

最大混雑度は、実世界の「人 / ㎡」を推定するものではなく、**異なる条件を同じ基準で比較するための簡易的な指標**として使っています。

#### 乱数条件の分離

シミュレーションでは、通行人の初期位置などに乱数を使います。また、GAによる配置探索にも乱数が使われます。

乱数条件が毎回変わると、結果の違いが「移動モデルの違い」なのか「たまたま初期位置が違っただけ」なのか判断しづらくなります。

そこで、乱数を以下の2つに分けています。

- `simulation_seed`：通行人の初期位置など、シミュレーション側の乱数条件
- `optimizer_seed`：GAの候補生成・選択・交叉・突然変異など、探索側の乱数条件

同じシナリオ・設定・seedを指定することで、同じ条件から評価や探索をやり直せるようにしています。

### 4. シミュレーション結果を使った壁配置探索

人流を観察・評価するだけでなく、その結果を使って、**どの壁配置が比較的良い結果になるか**も探索できるようにしました。

GA（遺伝的アルゴリズム）は、複数の配置候補を作り、それぞれを評価しながら、より評価の良い候補を残して新しい候補を作る処理を繰り返します。

本システムでは、候補となる壁配置ごとに描画なしで人流シミュレーションを実行し、

- 到達までに時間がかかりすぎないか
- 強い混雑が起きていないか
- 到達できない人が増えていないか

をもとに配置の良し悪しを判定します。

探索後は、**探索開始時の現在配置**と探索で得られた最良候補について3指標を並べて比較し、ユーザーが選択した場合のみ最良候補をライブマップへ適用します。

```text
壁配置の候補を生成
      ↓
描画なしで人流シミュレーションを実行
      ↓
配置の評価値（Fitness）を計算
      ↓
評価のよい候補を残して新しい候補を生成
      ↓
繰り返し
```

#### 壁配置の制限

壁を自由にどこへでも移動できると、単に人の進路から遠ざける配置が有利になりやすくなります。

そこで、**配置可能領域（Placement Zone）**を設定し、その中だけで壁を移動させます。

また、

- 壁同士が重ならない
- 出発地・目的地と重ならない
- マップ外へ出ない
- いずれかの人流について目的地までの経路を完全に塞がない
- 元の壁形状を変えない
- 基準位置から一定範囲内で移動する

といった制約を設けています。

#### 補足：Fitness

GA では **Fitness** という評価値を設定し、Fitness の値をもとにして GA による計算結果を評価します。
今回の場合、**Fitnessは、1つの壁配置がどの程度よいかを候補同士で比較するための評価値**ということになります。
本システムで設定した Fitness は以下の通りで、値が小さいほど良い配置としています。

```text
Fitness
=
平均到達時間
+ 混雑ペナルティ
+ 未到達ペナルティ
```

（⭐️不要？）平均到達時間だけで評価すると、移動が速い一方で一部に強い混雑が発生したり、時間内にゴールへ到達できないエージェントが増えたりする配置を十分に不利にできない可能性があります。そのため、**到達までの速さを中心に、混雑と未到達にもペナルティを加えて候補を比較**します。

（⭐️不要？）ここで、Fitnessは「有効な配置の中でどれがより良いか」を比較するために使います。一方、**壁同士が重なる、スタート/ゴールを塞ぐ、マップ外へ出る、移動可能範囲を超える**といった配置は、Fitnessで競わせる前に無効な候補として除外します。

### 5. 実際に動かして見つかった課題を、探索条件へ反映（⭐️不要？）

#### 課題1：自明な壁配置場所（かなり細かい話。突っ込まれたら回答できるようにしておく。）

壁配置探索を実際に動かすと、壁を自由にどこへでも移動できる場合、人流を邪魔しないマップ端へ壁を退避させる候補が有利になりやすいことが分かりました。また、壁をセル単位で独立に扱うと、ユーザーが作った壁形状が探索中に崩れてしまいます。

そこで、**配置可能領域（Placement Zone）**を設け、その範囲の中だけで壁配置候補を探索するようにしました。

- **壁グループ（WallGroup）**  
  1回のドラッグで連続配置した壁セル群を1つの論理オブジェクトとして扱います。内部では基準位置 `origin` と、その位置からの相対セル座標 `cells` を保持します。
- **壁形状の維持**  
  手動移動・GAによる配置探索のどちらでも相対座標は変更せず、グループ全体を平行移動します。回転・拡大縮小・分割は行いません。
- **配置可能領域と移動範囲**  
  WallGroupの全セルがPlacement Zone内に収まることを条件とし、さらに基準位置から一定範囲内だけ移動可能とします。
- **配置制約**  
  WallGroup同士の重複、各人流の出発地・目的地との重複、マップ外への配置、いずれかの人流について目的地までの経路を完全に遮断する配置を無効とします。

WallGroupやPlacement Zoneは、**ユーザーが作った壁形状を保ちつつ、現実的な設計可能範囲の中で配置探索を行うためのデータモデルと制約**として位置づけています。

#### 課題2：限定的な人同士の相互作用（工夫した点の 1番に含めているので、不要かもしれない。）

単純な一方向流だけでは人同士が異なる方向から交わる状況が少ないため、基本シナリオに加えて **対向流・交差流** を追加しました。異なる人流に属する通行人も同じ局所回避の対象とし、近距離では距離に応じて反発を強めています。

## このプロジェクトで重視したこと

本プロジェクトでは、

**移動ルールをモデル化する → ブラウザで集団挙動を観察する → 条件を変えて同じ指標で比較する → シミュレーション結果を使って環境配置を探索する**

という一連の検証フローを、一つのシステムとして扱います。

単一のアルゴリズムを実装することではなく、**数理モデルを交換可能な形で実装し（⭐️数理モデルと言い切ってしまって良いのか…？）、比較条件を揃えて評価し、得られた結果を次の探索処理へ接続するところまでソフトウェアとして構成すること**を、このプロジェクトの中心に置いています。

（⭐️要件定義が甘いと取られる可能性。または、スペースを割いて載せるべき内容でもないか？）さらに、実際にシミュレーションを動かした結果から、探索空間や人流条件の問題を見つけ、壁を配置できる場所に制限を設けたり、複数人流シナリオを追加するなど、**観察結果をもとにモデルや問題設定そのものを見直すこと**も意識しています。

## 現在の状況・制限事項

現在は、**一方向流・対向流・交差流のシナリオ、4通りの移動モデル比較、3指標による定量評価、配置可能領域内でのGAによる制約付き壁配置探索**を中核機能として実装しています。

（⭐️以下の制限事項は書いた方が良いか…？あえてマイナスを書いている気がする。）現実の人流データを用いたパラメータ校正や妥当性検証は行っておらず、実世界の人流予測や安全判断を目的としたシステムではありません。最大混雑度も実際の人口密度を推定する値ではなく、条件間を比較するための簡易指標です。壁オブジェクトについても、実際の建築壁そのものではなく、配置変更可能な仮設パーティション等を簡略化したモデルとして扱っています。
