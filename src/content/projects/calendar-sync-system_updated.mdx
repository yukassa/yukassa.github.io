## Overview

全社的なGoogle Workspace導入に伴い、APIを持たない既存の社内カレンダーシステムとの並行運用期間が発生しました。

本プロジェクトでは、Googleカレンダーの予定変更を検知し、スクレイピングを用いて既存の社内カレンダーへ自動連携する基盤を構築しました。

## Architecture

Google Calendarからの変更通知を起点に、**データ変換・キューイング・スクレイピングを分離したイベント駆動構成**としました。失敗しやすいスクレイピング処理を専用のLambdaへ分離し、同期対象データと処理状態をDynamoDBで管理します。

_Figure: SQS FIFOによる予定単位の順序制御と、DynamoDBによる状態管理を組み合わせた非同期同期アーキテクチャ。_

1. Webhook受信: Google Calendarの変更通知をAPI Gatewayで受信し、Logic Lambdaを起動。
2. データ保存: Logic Lambdaで予定データを取得・正規化し、DynamoDBへ同期対象データと初期ステータス PENDING を保存。
3. キュー投入: SQS FIFOへ同期処理を投入。Message Group IDを User × Event 単位とし、同一予定の処理順序を維持。
4. スクレイピング処理の起動: SQSからスクレイピング用Lambdaを起動。同時実行数を制御し、旧システムへのアクセス集中を抑制。
5. 処理開始: スクレイピング用LambdaがDynamoDBから同期対象データを取得し、ステータスを PROCESSING に更新。
6. 旧システムへ反映: APIを持たない旧社内カレンダーへスクレイピングで予定を反映。
7. 完了・失敗処理: 処理結果に応じてステータスを DONE / FAIL に更新。一時的な失敗はSQS経由で再試行し、再試行上限を超えたメッセージはDLQへ移動。タイムアウト等で状態更新まで到達しなかった処理も、DynamoDB上の未完了状態から確認可能とする。

## My Role

3名体制のプロジェクトで**プロジェクトリーダー兼開発者**を担当し、要件整理・アーキテクチャ設計・コアロジック実装を担当しました。

特に、 **「同一予定に対する操作順序を守ること」と「ある予定の失敗が無関係な予定を止めないこと」** の両立を重視して設計しました。

- **アーキテクチャ設計:**  
  Google Calendar側のデータ変換・整合性処理と、失敗しやすいスクレイピング処理を別Lambdaへ分離する非同期連携構成を設計しました。
- **キュー設計・流量制御:**  
  SQS FIFOのMessage Group IDを **User × Event** 単位で設計し、同一予定内の順序を保ちながら、無関係な予定を独立して処理できる構成としました。また、スクレイピング用Lambdaの同時実行数を制御し、連携先への過度な同時アクセスを抑える流量制御を設計しました。
- **コアロジック実装:**  
  Google Calendarの仕様解析、予定データの正規化、DynamoDBを用いた同期状態管理などをGoで実装しました。

## Technical Challenges & Solutions

### 1. データ変換とスクレイピングの責務分離

Google Calendarのデータ変換・整合性処理と、タイムアウトや画面変更の影響を受けやすいスクレイピングを同一プロセスで扱うと、スクレイピングの失敗時に変換処理まで再実行する必要があります。

- **Solution: Logic / Worker Split**  
  処理を2つのLambdaへ分割しました。
  1. **Logic Lambda:** データ変換と整合性チェックを行い、正規化データをDynamoDBへ保存して、同期対象をSQSへ投入。
  2. **Worker Lambda:** キューから同期対象を受け取り、既存システムへのスクレイピング処理に専念。

  これにより、失敗時の再処理範囲をスクレイピング側へ限定し、変換ロジックとIO処理を個別にテストしやすくしました。

### 2. FIFOの順序保証と処理の独立性

当初、ユーザー単位で順序制御すると、ある予定の同期が失敗した場合に、そのユーザーに属する別予定の後続処理まで詰まるリスクがありました。

- **Solution: User × Event Message Grouping**  
  SQS FIFOのMessage Group IDを **「ユーザーID × 予定ID」** 単位にしました。

  これにより、同一予定に対する「作成 → 変更」の順序を維持しつつ、特定予定の失敗が他の無関係な予定同期を阻害しにくい構成としました。

- **Solution: Concurrency Control**  
  スクレイピング用Lambdaの同時実行数を制御し、APIを持たない既存システムへのリクエスト集中を抑える構成としました。

### 3. 失敗を前提とした状態管理と復旧

スクレイピングは画面構成の変更やタイムアウトなどにより失敗する可能性があります。すべてを自動復旧させるのではなく、**失敗を検知し、必要に応じて人手のリカバリへつなげられること**を重視しました。

- **Solution: DynamoDB Status Management**  
  同期対象ごとに PENDING / PROCESSING / DONE / FAIL の処理状態をDynamoDBへ記録し、一定時間完了していない予定を抽出できるようにしました。
- **Solution: Retry / DLQ / Manual Recovery**  
  一時的な失敗は再試行し、自動復旧できない処理はDLQへ退避。状態管理と組み合わせることで、手動リカバリが必要な対象を把握できる運用フローとしました。

## Results

- **非同期連携基盤の実装:** Google Calendarから旧社内カレンダーへの連携を、Go / AWSを用いた非同期処理基盤として構築しました。
- **障害影響の局所化:** SQS FIFOのMessage Group IDをUser × Event単位にすることで、特定予定の失敗が無関係な予定の処理を阻害しにくい構成としました。
- **復旧可能な運用:** DynamoDBによる同期状態管理とDLQを組み合わせ、自動復旧できない処理を特定し、手動リカバリへつなげられるようにしました。
