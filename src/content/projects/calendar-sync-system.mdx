## 概要

全社的なGoogle Workspace導入に伴い、APIを持たない既存の社内カレンダーシステムとの並行運用期間が発生しました。

本プロジェクトでは、Googleカレンダーの予定変更を検知し、スクレイピングを用いて既存の社内カレンダーへ自動連携する基盤を構築しました。特に、**失敗しやすい外部I/Oを分離し、予定ごとの順序を守りながら、1件の失敗が他の予定へ波及しにくい構成にすること**を重視しました。

## システム構成

Google Calendarからの変更通知を起点に、**Webhook受信・データ変換と、既存システムへのスクレイピングをSQS FIFOで分離するイベント駆動構成**としました。

_Figure: SQS FIFOによる予定単位の順序制御と、DynamoDBによる状態管理を組み合わせた非同期連携アーキテクチャ。_

1. **Webhook受信**  
   Google Calendarの変更通知をAPI Gatewayで受信し、`subscribeGoogle` Lambdaを起動。
2. **予定データの取得・保存**  
   Google Calendar APIから差分予定を取得・正規化し、DynamoDBへ同期対象データと初期状態 `PENDING` を保存。
3. **キュー投入**  
   SQS FIFOへ予定単位で同期処理を投入。Message Group IDを **User × Event** 単位とし、同一予定に対する操作順序を維持。
4. **スクレイピング処理の起動**  
   SQSから `applyDesknets` Lambdaを起動。スクレイピングの同時実行数に上限を設け、連携先へのアクセス集中を抑制（SQS Event Source Mapping `maximum_concurrency = 150`、Lambda Reserved Concurrency `= 200`）。
5. **予定同期処理の開始**  
   DynamoDBから同期対象を取得し、予定の同期状態を `PROCESSING` に更新。
6. **旧システムへ反映**  
   APIを持たない旧社内カレンダーへスクレイピング処理で予定を反映。
7. **完了・失敗処理**  
   成功時は `DONE`、失敗時は `FAIL` として予定の同期状態を追跡。処理できなかったメッセージはDLQへ隔離し、後から確認・復旧できるようにしました（Visibility Timeout `= 360秒`、`maxReceiveCount = 1`）。

## 担当・役割

3名体制のプロジェクトで**プロジェクトリーダー兼開発者** を担当し、要件整理・アーキテクチャ設計・コアロジック実装を担当しました。

特に、 **「同一予定に対する操作順序を守ること」と「ある予定の失敗が無関係な予定を止めないこと」** の両立を重視して設計しました。

- **アーキテクチャ設計**  
  Google Calendar側の差分取得・データ変換と、失敗や処理時間の変動が大きいスクレイピング処理を別Lambdaへ分離する非同期構成を設計しました。
- **キュー設計・流量制御**  
  SQS FIFOのMessage Group IDを **User × Event** 単位で設計し、同一予定内の順序を保ちながら、無関係な予定を独立して処理できる構成としました。また、スクレイピング処理の同時実行数に上限を設け、連携先への過度な負荷を抑えるようにしました。
- **コアロジック実装**  
  Google Calendarの仕様解析、予定データの正規化、DynamoDBを用いた同期状態管理などをGoで実装しました。
- **IaC・CI/CD**  
  LambdaをDockerコンテナイメージとして構築し、Amazon ECRへ格納する構成としました。AWSリソースとLambdaのデプロイをTerraformでIaC化し、GitHub Actionsから一連のデプロイを自動実行できるCI/CD環境を構築しました。

## 技術的な課題と工夫

### 1. 失敗しやすい外部I/Oを分離する

- **課題**  
  Google Calendarの差分取得・データ変換と、タイムアウトや画面変更の影響を受けやすいスクレイピングを同じ処理で扱うと、既存システム側の失敗によって前段の処理まで再実行する必要があります。
- **対応**  
  Webhook受信・差分取得を担う `subscribeGoogle` と、既存システムへの反映を担う `applyDesknets` を別Lambdaとして実装し、SQS FIFOを介して非同期に分離しました。
- **効果**  
  **不安定な外部I/Oの影響範囲をスクレイピング側へ限定**し、Google Calendar側のデータ取得・変換処理と、既存システムへの反映処理を独立して扱える構成としました。

### 2. 予定単位の順序保証と処理の独立性を両立する

- **課題**  
  ユーザー単位で処理順序を制御すると、1件の予定同期が失敗した場合に、同じユーザーの別予定まで後続処理が詰まる可能性があります。一方で、同じ予定に対する作成・変更などの操作順序は維持する必要があります。
- **対応**  
  SQSのデータ保存の単位を **「ユーザーID × 予定ID」** に設定しました（SQS FIFOの`Message Group ID`）。
- **効果**  
  同一予定に対する「作成 → 変更」の順序を維持しつつ、異なる予定は独立して処理できるようにしました。これにより、**特定予定の失敗が他の予定へ波及しにくい処理**を実装しました。

### 3. 連携先へのアクセス集中を防ぐ

- **課題**  
  予定変更が集中すると、SQSに多くの動機処理が蓄積します。それらを無制限に並列実行すると、スクレイピング先の既存システムへ短時間に大量のアクセスが発生する可能性があります。
- **対応**  
  スクレイピングの同時実行数に上限を設けました（SQS Event Source Mappingの `maximum_concurrency`、Lambdaの`Reserved Concurrency`）
- **効果**  
  キューに処理が集中した場合でも、連携先システムへ一度に大量アクセスを発生させない構成としました。

### 4. 失敗を追跡し、復旧できる状態にする

- **課題**  
  スクレイピングは、画面変更やタイムアウトなどによって失敗する可能性があります。そのため、単に再施行するだけでなく、**どの予定がどこまで処理されたかを把握し、必要に応じて復旧できること**が必要でした。
- **対応**
  - **予定の同期状態の管理**  
    DynamoDBで同期対象の予定を `PENDING / PROCESSING / DONE / FAIL` の状態として管理し、各予定の処理状況を追跡できるようにしました。
  - **失敗した予定の隔離と復旧**  
    処理できなかったメッセージは、SQSのRedrive PolicyによってDLQへ隔離します。DynamoDBの状態管理と組み合わせることで、確認・リカバリが必要な対象を把握できるようにしました。
  - **監視・通知**  
    CloudWatchでLambda / API Gatewayのエラー、タイムアウト、同時実行数、Chromium起動失敗などを監視し、Slackへ通知する運用フローを構築しました。
- **効果**  
  処理の連携状態を追跡し、**状態の追跡 → 異常の検知 → 対象の特定 → 手動復旧**までつなげられる構成としました。

## 継続的な運用のために工夫したこと

Google CalendarのWebhookチャンネルには有効期限があるため、定期的に再購読する処理も実装しました。また、Webhook受信処理が失敗した場合はアプリケーション側で独自の再試行処理を追加せず、非2xxレスポンスに対するGoogle Calendar側の再送を利用する構成としました。

これらは主機能ではありませんが、**継続運用を前提に外部サービス固有の制約まで設計へ組み込んだ例**です。

## 成果

- **非同期連携基盤の実装**  
  Google Calendarから旧社内カレンダーへの予定連携を、Go / AWSを用いた非同期処理基盤として構築しました。
- **障害影響の局所化**  
  SQS FIFOのMessage Group IDをUser × Event単位にすることで、同一予定の順序を維持しながら、特定予定の失敗が無関係な予定へ波及しにくい構成としました。
- **連携先への負荷制御**  
  スクレイピング処理の同時実行数を制御し、処理量が増えた場合でも既存システムへのアクセス集中を抑えられるようにしました。
- **復旧可能な運用**  
  DynamoDBによる状態管理、SQS DLQ、CloudWatch監視を組み合わせ、異常を検知して手動リカバリへつなげられる構成としました。
