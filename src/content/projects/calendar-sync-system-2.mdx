## Overview

全社的な Google Workspace 導入に伴い、API を持たない既存の社内カレンダーシステム（SaaS）との並行運用期間が発生しました。
本プロジェクトでは、Google カレンダーの予定変更を検知し、スクレイピングを用いて旧システムへ自動同期する連携基盤を構築しました。

## My Role

**プロジェクトリーダー兼リードエンジニア**として、3 名体制のチームを牽引しました。
不安定な外部システム（スクレイピング必須・API なし）との連携において、こちらのシステム側で最大限の可用性を担保するための**アーキテクチャ設計（キュー粒度の最適化・流量制御）**と、**Go 言語による堅牢な実装**を主導しました。

## Technical Challenges & Solutions

### 1. ブロッキング問題の解消 (Granular Queueing)

当初は「ユーザー単位」での順序制御を検討しましたが、ある予定の同期がスクレイピングエラーで失敗すると、そのユーザーの以降の同期処理が全て詰まる（Head-of-Line Blocking）リスクがありました。

- **Solution: User x Event Partitioning**
  SQS FIFO のメッセージグループ ID を**「ユーザー ID + 予定 ID」**の組み合わせで設計しました。
  これにより、「同一予定に対する操作（作成 → 変更）」の順序整合性は担保しつつ、**特定のエラーが他の無関係な予定同期を阻害しない並列性**を実現しました。

### 2. 外部システムの保護と流量制御 (Throttling)

連携先の SaaS は親会社も利用する重要システムであり、過度なアクセスによるダウンは許されない環境でした。しかし、システム的なスループット制限値は公開されていませんでした。

- **Solution: Heuristic Concurrency Control**
  AWS Lambda の **予約済み同時実行数** を活用して「バルクヘッド（隔壁）」を構築。運用しながらエラーレートを監視し、連携先 SaaS が応答可能なギリギリの並列数にチューニングを行うことで、システムダウンリスクを回避しつつ処理能力を最大化しました。

### 3. 不確実性への対処 (Error Handling)

スクレイピングは画面構成の変更やタイムアウトにより、必然的に失敗する可能性があります。

- **Solution: Robust Retry & DLQ**
  一時的なタイムアウトに対してはエクスポネンシャル・バックオフによる自動リトライを実装。それでも成功しない永続的なエラーは **Dead Letter Queue (DLQ)** へ隔離し、ログ基盤と連携することで、「どの予定が失敗しているか」を運用担当者が即座に追跡できる可観測性（Observability）を確保しました。

## System Architecture

完全なサーバーレスアーキテクチャ（Go on Lambda）を採用しました。

1.  **Ingest:** Google Calendar API Webhook を受信。
2.  **Queue:** **「予定単位」**の ID で Amazon SQS (FIFO) へエンキュー。
3.  **Process:** Lambda (Go) がキューを取得し、スクレイピングを実行。
4.  **Resilience:** 失敗時はリトライを行い、最終エラーは DLQ へ送出しアラート発報。

## Results

- **実装成果:** 複雑なステート管理（同期状態・ID マッピング）を含むバックエンドロジックを Go 言語でフルスクラッチ開発。
- **運用改善:** 頻発するスクレイピングエラーに対し、DLQ とログ分析により「失敗した予定」を特定可能にし、手動リカバリが必要なケースの判断迅速化に貢献。
